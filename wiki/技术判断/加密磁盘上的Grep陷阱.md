# 加密磁盘上的 Grep 陷阱

**现象**：在一个确定存在的符号上跑 Grep，返回空。不报错，就是零命中。你会以为符号不存在、类没被引用、代码被谁删了，然后开始怀疑自己。

**原因**：那台机器的磁盘做了透明加密，而且是进程白名单型的——只有被授权的进程（IDE、编辑器）能从磁盘拿到明文，其他进程（rg、grep、findstr，甚至自己写的脚本）读到的都是密文。密文里搜不到任何源码符号，所以 Grep 永远返回空。

**怎么发现的**：用 Grok bot 跑测试时发现的。同一个文件，Grep 说没有，读出来内容清清楚楚。两边对不上，才想到不是符号的问题，是读取通道的问题。

**判断方法**：对一个你确定存在的符号 Grep，零命中就当作加密环境处理，不要再怀疑符号本身。这个信号很干脆，一旦出现就不必再试第二次。

**怎么处理**：

- 定位只走 Read，可以按行段读，不要整文件通读。
- 不要再对源码目录跑 rg / grep / findstr，也不要为了找引用写临时脚本——全都读到密文，白跑还烧时间。
- 要看谁引用了它，改用未加密的调用方（测试代码、非加密模块）去搜。

这条规则现在写在 `readability-loop` 的 SKILL.md 里，原文是"禁止再对源码目录 Grep/rg/findstr，定位只能 Read"。

**边界**：不限于某一个项目。只要换到一台有透明加密的机器，规则立即成立——这也是它该待在通用层、而不是某个项目的约定文件里的原因。

这篇记的是同一个根因（亿赛通透明加密）的两个面：**工具读不到源码**，和**文件本身就是密文**。

## 密文本身长什么样

Grep 返回空是"读的时候"出问题。还有一种更彻底的情况——文件本身就是密文，存的就是密文，不是读取方式的问题。

2026-10 从微信收到一份 ag6.0 的工程，里面 19 个 `.kt` 全部是加密的。特征很整齐，三个文件的头完全一致：

```
偏移 0   62 14 23 65      4 字节魔数
偏移 4   ?? ?? ?? ??      每文件不同
偏移 8   00 00 00 01      固定
偏移 12  "E-SafeNet"      明文字面量
偏移 24  "LOCK"           明文字面量
```

判据：开头是 `62142365`，并且前 64 字节里出现 ASCII `E-SafeNet`。两条同时满足就判亿赛通，比看熵靠谱。

三个实测结论：

- **整份都是密文**。用 strings 搜不到 `package`、`import`、`class`、`fun` 里的任何一个，没有残留明文，非授权终端救不回来。
- 文件比原文大，多出来的是头部和分块填充。
- 熵 7.7~7.9。正常文本 4~6.5，所以熵能当粗筛，但不如指纹干脆。

## 怎么拦住它被提交上去

已经做成工具了，在技能库 `tools/check-plaintext.mjs`。装一次钩子，之后每次提交自动检查：

```
git config core.hooksPath .githooks
```

两个判断值得记住：

**一、检查暂存区，不检查磁盘文件。** 磁盘上读到明文还是密文，取决于哪个进程被加密软件授权；暂存区的字节才是真正推上 GitHub 的东西，用 `git show :路径` 取。检查它，等于检查答案本身。

**二、按提交记录增量扫。** 把上次扫完的 HEAD 记下来，下次只用 `git diff` 算出改动过的文件。**没通过就不推进记录**，下次重扫同一批，不会漏。

## 一条容易犯的错

判断编码时不要只解码文件前几千字节就下结论。第一次扫描时截断了 8192 字节，正好切在汉字中间，把 5 个正常文件误报成密文，差点连带去改 token 和仓库结构。

**截断的样本不能用来判断编码。** 这个错和"Grep 零命中就怀疑符号不存在"是同一类：都是拿不完整的信息下结论。

## 检查工具该放在哪

加密还会影响一件很隐蔽的事：**检测密文的工具，自己也可能被加密。**

第一版把检查脚本放在仓库里（`tools/check-plaintext.mjs`），git 钩子调它。看起来合理，实测是错的。

把脚本自己换成密文再提交，钩子确实拒绝了提交——方向没错，fail-closed。但它打印的是：

```
提交已取消：暂存区里有不是可读文本的文件
```

**坏掉的是检测器，它却在指控你的文件。** 会去翻文件、查不出问题，最后 `--no-verify` 绕过。一次误诊就足以让人不再信任这个钩子，此后它每次报警都会被当成误报。

所以：**检测器不能住在被检测的区域里。**

现在分三层，各自不依赖对方：

| 层 | 位置 | 跑在哪 | 失效时会怎样 |
|---|---|---|---|
| 提交前 | `~/.git-hooks/pre-commit`，仓库外 | 本机 | 仍然拦下提交，但诊断可能是错的 |
| 推送后 | `.github/workflows/text-guard.yml`，逻辑内联 | GitHub 的机器 | 不受本地加密影响 |
| 手动 | 同一个钩子的 `--all` / `--dir` | 本机 | 立刻暴露 |

几个具体决定：

- **钩子放仓库外**，用 `git config --global core.hooksPath ~/.git-hooks` 启用。不会被 `git pull` 覆盖，不随仓库更新漂移，仓库目录被加密时也不受牵连。
- **逻辑内联在一个文件里**，不 import 外部模块，不读仓库里的任何脚本。判据、遍历、输出全在这一个文件里，复制过去就能跑。
- **CI 的逻辑写在 workflow 里**，不引用仓库里的 `.mjs`。云端 checkout 出来的文件不可能被加密，那一层天然可信。
- **装完必须手动跑一次 `--all`**。钩子坏掉之后不会主动告诉你，它只会给出错误的诊断。这一步是唯一能发现"装了个坏的"的机会。

第三条有个权衡值得说清：CI 逻辑内联，等于同一套判据存在两处（钩子一份、workflow 一份），有漂移风险。但换成引用仓库里的脚本，就把云端也拖进了"脚本可能被加密"的问题里——而云端本来是整个体系里唯一干净的一环。宁可维护两份代码，也不让干净的那层染上依赖。

### 怎么确认它真的在跑

装好不等于接上。有三种静默失效，都不会报错：

- `core.hooksPath` 没配 → git 用默认的 `.git/hooks`，那里没有这个文件，跳过
- 配了但指向一个已经不存在的目录（比如仓库里那个被删掉的 `.githooks`）→ 同样跳过，连警告都没有
- 配了 `~` 而 shell 没有展开 → git 把 `~` 当字面量，路径不存在，跳过

第三种最坑：`git config --global core.hooksPath "~/.git-hooks"` 加了引号就不会展开，配置看着成功，实际永远不会跑。

所以给钩子加了 `--doctor`：

```
钩子文件    明文  6617B  C:\Users\...\.git-hooks\pre-commit
全局配置    C:/Users/.../.git-hooks
当前仓库    C:/某仓库
结论        已接上，每次提交都会自动检查
```

它核对三件事：钩子文件本身是不是明文、`core.hooksPath` 指向哪个目录、那个目录下的 `pre-commit` 是不是就是它自己。任何一项不对就报「没接上」，并直接给出该执行的命令。

有一种情况它盖不住——**钩子自己变成密文时，这个命令根本跑不起来**，报的是 `cannot execute binary file` 或 `Exec format error`。这反而好认：错误指向的是钩子文件，不是你的内容。而旧设计下，同样的情况下报的是「你的文件不是明文」，指向的是内容。**同一个故障，错误信息指向谁，决定了你要花多久才能修好。**

### 一个容易忽略的事实

**通过 API 直接提交时，本地钩子完全不参与。**

API 提交不经过 `git commit`，只是在服务端建对象、移动分支指针。让 AI 直接写仓库走的就是这条路——它绕得过本地钩子，绕不过云端 workflow。

所以三层里，只有云端那层覆盖了所有提交方式。本地那层的作用是"让你当场知道"，不是"保证最终正确"。把这两件事混在一起，就会出现"我装过钩子了"这种虚假安全感。

## 换个角度看这件事

这两次踩的坑其实是同一个形状：

- Grep 零命中，以为符号不存在 —— 读的通道有问题，怪内容
- 编码校验报错，以为文件坏了 —— 样本被截断了，怪数据
- 检测脚本报"你的文件不是明文" —— 脚本自己坏了，怪文件

**每一次都是工具出了问题，然后在指控被检测的对象。** 这个形状在任何自检系统里都会重演：校验器、linter、健康检查、监控探针。它们的共同弱点是——失败时倾向于说"输入有问题"，因为那是它们唯一会做的判断。

能防的办法只有一条：**让检测器和被检测物没有共同的失效原因。** 住同一个磁盘、同一个仓库、同一个加密策略，就必然会一起坏；一起坏的时候，它给出的结论一定是错的。
