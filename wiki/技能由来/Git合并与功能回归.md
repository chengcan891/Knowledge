# Git 合并与功能回归\n\n`git-merge-function-check` 解决的不是“怎么把冲突标记清掉”，而是合并之后怎样证明两边原有的功能还活着。\n\n## 起因\n\n一次长分支整理里，很多文件没有产生冲突，或冲突很快就解完了；真正危险的是自动合并、删改同处和依赖替换：Git 能得到一个可提交的版本，却不知道原来的入口、失败处理、注册或资源是否还连得上。提交数量对齐、工作区干净、甚至静态检查通过，都不是功能完整的证据。\n\n## 这套检查怎么做\n\n开始前先记住两侧提交点、共同基线和用户原有改动。逐处把两边相对基线新增的行为拆开，看入口、调用链、默认值、错误分支、配置、依赖和结果分别落到哪里。\n\n最需要放慢的是“一边删、一边改”：先弄清删除是否已有替代，再确认替代位置真的能被调用；只有明确废弃，或能证明无调用且没有遗漏行为时，才能接受删除。二进制依赖也不能按文件大小或时间猜，至少要对照接口、调用方和实际构建结果。\n\n每一轮结束都核对最终差异，而不是只看冲突文件。合并、变基或改写 HEAD 后，旧验收结论失效，必须重新验收。独立验收要由未参与合并的新观察者做只读检查；做不到时只能写“自检”，不能叫通过。\n\n## 验收边界\n\n静态调用链核对、编译和实机回归是三层不同证据。能证明到哪一层就写到哪一层；验收中止、超时或跳过，都要保留未覆盖的风险。发现合并引起的问题后，除了修复，也把它补到最早能发现它的检查步骤里。\n
