# 技能清单与由来

八个技能都在 https://github.com/chengcan891/AI 。这里不放技能本身，只放"它为什么存在"。

这一页装两组技能的来历。第三组进来的时候，把它拆成独立页面。

| 技能 | 解决什么问题 | 由来 |
|---|---|---|
| readability-loop | 编排拆分与验收，带着一个类从头走到通过 | 已记，见下 |
| readability-refactor | 拆超大类，补方法和属性注释 | 同上 |
| readability-review | 拿 rubric 独立验收，不通过就退回 | 同上 |
| feature-add-loop | 一个需求从讨论到落地的闭环 | 已记，见下 |
| feature-discuss | 动手之前的讨论与方案比较 | 同上 |
| feature-implement | 按讨论结论实现 | 同上 |
| feature-review | 实现后的复查 | 同上 |
| project-conventions-ag60 | 某个项目的专属约定，换项目整份替换 | 同上（它是参数，不是流程） |

## 可读性三段式

**起因**：agmap 那个项目里类的创建失控了。类越写越大，职责堆在一起，方法和属性没有注释，后来的人—包括三个月后的自己—读不动。

**要办的两件事**：拆分类，补注释。

**为什么拆成三个技能**：不能只丢一句"帮我改一下"。一次改太多必然改坏，改坏了又没人能判断到底有没有改坏。所以分成三个角色：

- 一个负责**编排**：定这一轮动哪几个文件、什么时候停
- 一个负责**拆**：按职责切开，顺手补上方法和属性注释
- 一个负责**验收**：拿 rubric 独立判断过没过，不过就退回重改

**核心约束**：动手的和验收的不能是同一方。同一个视角既改又判，永远会说"改好了"。

**边界**：只对"已经大到读不动、但还在被频繁修改"的类成立。一次性的、不会再碰的旧代码，拆它没有收益。

## 需求四段式与项目约定

**起因**：ag6.0 这个项目要不断加新功能。每加一个，路数都一样——先讨论清楚要做什么，再实现，再复查。同样的路走第二遍就开始重复，于是固化成四个技能。

**四段各管什么**：

- `feature-add-loop` 编排：一个需求从进入到算完，中间该停在哪几处
- `feature-discuss` 讨论：动手之前把要做的事和几个备选方案说清楚
- `feature-implement` 实现：按讨论结论写
- `feature-review` 复查：写完之后对着结论核一遍

**关键设计：流程里不写项目信息**。四段式本身不含任何 ag6.0 的内容，路径、基类、命名、样式全在 `project-conventions-ag60` 里。所以换一个项目，是换那份约定文件，流程一行都不用改。

**为什么非这么分不可**：如果流程里写死了 ag6.0 的路径和基类，到新项目就得复制一份改。复制之后两边各自演进，第三次修改的时候已经分不清哪版是对的。**把"怎么做"和"在哪做、按什么规矩做"分开，才是能复用的前提。**

**现状**：还没在第二个项目上真跑过。"能在其他项目加新功能"目前是设计意图，不是已验证的事实。这个区别要记住——没验证过的复用性，第一次用的时候大概率要改。

## 流程和参数是两层

`project-conventions-ag60` 不是技能，是**参数文件**。它和四段式的关系就是「流程 + 配置」。

它含项目专属的路径、基类、样式类，所以天然随项目消失、天然该整份替换。这不是缺陷，是它存在的理由。

它真正值钱的东西是这个项目**当初为什么这么定**，那属于项目档案，该进 `wiki/项目/`。等 ag6.0 上出现第一个"为什么这么定"的判断，就在 `wiki/项目/ag6.0.md` 建页。

## AI 进来之后

2026-10 起，ag6.0 的开发改成 Android Studio 加 codex / cursor，代码大部分由 AI 写。

这件事挪动了两组技能的处境：

- **需求四段式**：起因原来记的是"加功能的路数重复"，现在多了一条更硬的理由——AI 一次给不全，必须先在讨论那段停下来对齐。路数还是那个路数，但"停下来"从省事变成了必需。
- **可读性三段式**：起因被放大了。原来要治的是人把类写大了，现在要治的是这批代码不是自己写的、还得读。同一套拆类补注释的办法未必合用，没验证过。

具体现象和推论在 [AI 写完之后，谁来读、谁来验](../技术判断/AI写完之后谁来读谁来验.md)。

## 还欠着的

**可读性三段式**

- 多大算"大"。按行数、方法数，还是"改一次要翻几个文件"判断的。
- rubric 最初只有几条，后来一条条加上去的顺序是什么。
- 跑一轮大概多久，什么情况下会放弃整个过程改成局部修补。

**需求四段式**

- 约定文件里最少要有哪几项，四段式才跑得起来。构建命令、模块结构、基类、命名风格、哪些地方不能碰——这几项是不是够，还没试过。
- "讨论完了"的标准是什么。discuss 段现在产出的是文字还是清单，什么样算讨论够、什么样算还没想清楚。
- 换项目时做一次提炼：ag60 那份里哪些条款其实和项目无关、该提到流程层去。**这件事只能等真换项目才做得准。**
